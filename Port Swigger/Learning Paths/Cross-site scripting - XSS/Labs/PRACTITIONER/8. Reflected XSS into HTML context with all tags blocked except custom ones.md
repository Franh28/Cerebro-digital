### Punto de partida: ¿qué es distinto en este lab?

El título ya te da la pista: **"all tags blocked except custom ones"**. Es decir, el filtro tiene una lista de tags HTML _conocidos_ (`img`, `svg`, `body`, `script`, `a`, `div`...) y los bloquea todos. Pero como es una lista de tags **conocidos**, cualquier tag que **no exista** en HTML (uno inventado, tipo `<xss>`, `<foo>`, `<pepe>`) no está en esa lista, así que **pasa el filtro sin problema**.

### Paso 1: Fuzzing para descubrirlo (igual que antes)

Aunque la solución oficial no lo muestre, el proceso para llegar ahí es idéntico al lab anterior:

1. Mandas la petición de `search` a Intruder.
2. Pruebas con la lista de tags del cheat sheet → todos dan `400`.
3. Se te ocurre (o lo intuyes por el nombre del lab) probar un tag que **no existe** en HTML, tipo `<xss>` o `<foobar>`.
4. Ese tag da `200` → confirmas que el filtro es una lista de tags _válidos_, no analiza si el tag es real o inventado.

Ya tienes tu inyección base: `"><xss>` (cierras el contexto donde se refleja `search` e inyectas tu tag inventado).

### Paso 2: el problema — un tag inventado no hace nada por sí solo

Aquí está la parte interesante. `<img onerror=...>` funciona porque el navegador **intenta cargar** la imagen, falla, y dispara `onerror`. `<body onload=...>` funciona porque el navegador **carga la página** y dispara `onload`.

Pero `<xss>` no es un elemento real. El navegador no sabe qué hacer con él, no intenta cargar nada, no tiene comportamiento propio. Entonces: **¿qué evento puedes ponerle si no hace ninguna acción que dispare un evento automáticamente?**

Necesitas un evento que **cualquier elemento** pueda tener, sin depender de una acción "de carga". Candidatos típicos: `onmouseover` (pero requiere que la víctima mueva el ratón encima, poco fiable), `onclick` (requiere clic), **`onfocus`** (se dispara cuando el elemento recibe el foco).

### Paso 3: `onfocus` necesita que el elemento sea "enfocable"

Por defecto, solo ciertos elementos pueden recibir foco: enlaces, inputs, botones... Un `<xss>` inventado **no es enfocable por defecto**, así que aunque le pongas `onfocus`, nunca se disparará solo.

La solución: el atributo **`tabindex`**. Cualquier elemento con `tabindex` (aunque sea `tabindex="1"` o `tabindex="-1"`) se vuelve programáticamente enfocable. Con eso ya tienes:

html

```html
<xss id=x onfocus=alert(document.cookie) tabindex=1>
```

Ahora el elemento **puede** recibir foco y disparar `alert(document.cookie)` cuando lo reciba.

### Paso 4: ¿cómo le das el foco sin que la víctima haga clic?

Aquí viene el truco final. En HTML, si tu URL termina en `#algo` (un _fragment_/ancla), y existe un elemento con `id="algo"`, el navegador:

- hace scroll hasta ese elemento, **y**
- si el elemento es enfocable (gracias al `tabindex`), **le da el foco automáticamente**.

Por eso el `id=x` en el tag y el `#x` al final de la URL: en cuanto la página carga con esa ancla, el navegador enfoca el `<xss id=x>`, se dispara `onfocus`, y salta el `alert(document.cookie)`. Cero interacción del usuario necesaria.

### Paso 5: ¿por qué `location = '...'` en vez de un `<iframe>`?

En el lab anterior necesitabas el iframe porque el evento `resize` requería manipular el iframe desde fuera (cambiar su `width` con JS). Aquí no hace falta ese truco: el foco por ancla (`#x`) se dispara solo con **cargar la URL directamente**, así que basta con redirigir el navegador de la víctima a esa URL:

html

```html
<script>
location = 'https://YOUR-LAB-ID.web-security-academy.net/?search=%3Cxss+id%3Dx+onfocus%3Dalert%28document.cookie%29%20tabindex=1%3E#x';
</script>
```

- `%3Cxss...%3E` es tu payload URL-encodeado en el parámetro `search`.
- `#x` al final es el ancla que fuerza el foco automático.
- El `<script>location=...</script>` simplemente hace que el navegador de la víctima navegue a esa URL en cuanto visita el exploit server.
