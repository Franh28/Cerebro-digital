

### El problema de fondo

El parámetro `search` se refleja en el HTML, pero hay un filtro (WAF) que bloquea la mayoría de tags y atributos típicos de XSS (`<script>`, `onerror`, `onload`, etc). Necesitas encontrar **qué tag sí pasa** y **qué evento sí pasa**, para combinarlos.

### Pasos 1-2: Confirmar que hay un filtro

Pruebas el payload "de libro" (`<img src=1 onerror=print()>`). Si te lo bloquea (normalmente con un `400 Bad Request`), confirmas que no es un XSS trivial: hay una lista negra/blanca filtrando.

### Pasos 3-7: Fuzzing de tags con Intruder

- Mandas la petición de búsqueda a Intruder para poder automatizar pruebas.
- Pones `<§§>` como posición: esto le dice a Intruder "prueba metiendo cada payload de la lista **entre** los dos ángulos". Es decir, probará `<a>`, `<body>`, `<script>`, `<svg>`, etc., uno por uno.
- La lista de "tags" del cheat sheet es literalmente todos los tags HTML conocidos que se usan en vectores XSS.
- Lanzas el ataque y miras el **código de estado**: si el servidor bloquea el tag, responde `400`. Si el tag está permitido, responde `200` (la petición se procesó con normalidad, aunque no sepas aún si es explotable).
- Resultado: `<body>` es el único (o uno de los pocos) que pasa el filtro.

**¿Por qué `body` es interesante?** Porque `<body>` admite eventos como `onload` y `onresize` que se disparan sin necesidad de que el usuario haga clic en nada.

### Pasos 9-13: Fuzzing de atributos/eventos con el tag ya válido

- Ahora que sabes que `<body>` pasa, repites el proceso pero fuzzeando **qué evento** (`onload`, `onerror`, `onresize`, `onfocus`...) es aceptado dentro de ese tag: `<body §§=1>`.
- Pegas la lista de "events" del cheat sheet (todos los atributos `on*` conocidos).
- Resultado: `onresize` es el que pasa (probablemente porque el filtro bloquea `onload`, `onerror`, etc. por ser los más comunes, pero se olvidó de `onresize`).

Entonces ya tienes tu vector válido:

html

```html
"><body onresize=print()>
```

Esto cierra el atributo/contexto donde se refleja `search`, inyecta un `<body>` con el evento `onresize` ejecutando `print()`.

### El problema práctico: ¿cómo disparas un "resize" sin que la víctima haga nada?

Aquí está la parte más ingeniosa del lab. `onresize` normalmente se dispara cuando el usuario cambia el tamaño de la ventana del navegador — algo que la víctima no va a hacer voluntariamente solo porque visitó tu página.

**Solución: meter la página vulnerable dentro de un `<iframe>`, y cambiar el tamaño del iframe mediante JavaScript.** Cuando cambias el `width` de un iframe con JS, el documento _dentro_ del iframe recibe un evento `resize`, porque desde su perspectiva su "ventana" (el viewport del iframe) cambió de tamaño.

De ahí el exploit final:

html

```html
<iframe src="https://TU-LAB-ID.web-security-academy.net/?search=%22%3E%3Cbody%20onresize=print()%3E" onload=this.style.width='100px'>
```

- `src=...`: carga la página vulnerable con el payload ya inyectado vía el parámetro `search` (nota que va URL-encodeado: `%22` = `"`, `%3E` = `>`, `%3C` = `<`, `%20` = espacio).
- `onload=this.style.width='100px'`: en cuanto el iframe termina de cargar, cambia su propio ancho. Esto dispara el evento `resize` **dentro** del documento cargado en el iframe (la página del lab con tu `<body onresize=print()>` inyectado).
- Al dispararse `resize`, se ejecuta `print()` — y el lab detecta que se llamó a `print()` en el navegador de la "víctima" simulada, marcando el laboratorio como resuelto.

### Por qué "Store and Deliver" y no solo "View"

- **View exploit** carga la página solo en tu navegador de atacante, útil para probar que funciona, pero no cuenta para completar el lab.
- **Deliver to victim** simula que un usuario real visita tu URL del exploit server, con su propia sesión de navegador gestionada por PortSwigger. Solo así el sistema registra que el `print()` se ejecutó "en la víctima", que es la condición real para resolver el laboratorio (demuestra que puedes ejecutar JS arbitrario en el navegador de otra persona, no solo en el tuyo).
