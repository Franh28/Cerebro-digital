En la página base encontramos este script: 

```
<script>
	window.addEventListener('message', function(e) {
		var url = e.data;
		if (url.indexOf('http:') > -1 || url.indexOf('https:') > -1) {
			location.href = url;
		}
	}, false);
</script>
```


So:
```
<iframe src="https://0a1500ce042d30ad8216c4fb008e0049.web-security-academy.net/" onload="this.contentWindow.postMessage('javascript:print()//http:','*')">
```

Buena pregunta — este es un ejemplo clásico de cómo un chequeo de seguridad mal hecho se puede saltar.

**Qué hace el script vulnerable:**

js

```js
var url = e.data;
if (url.indexOf('http:') > -1 || url.indexOf('https:') > -1) {
    location.href = url;
}
```

La intención del desarrollador era: "solo permitas redirecciones a URLs que empiecen por `http:` o `https:`, para evitar que alguien use un esquema peligroso como `javascript:`".

El problema es que usa `indexOf('http:') > -1`, que solo comprueba que la cadena **`http:` aparezca en algún punto** del string — no que la URL _empiece_ por `http:`. No valida la posición ni el formato real de una URL.

**Cómo lo explota el payload:**

```
javascript:print()//http:
```

1. `url.indexOf('http:')` encuentra `http:` al final de la cadena → la condición se cumple (`> -1` es `true`).
2. El script ejecuta `location.href = url`, es decir: `location.href = 'javascript:print()//http:'`.
3. El navegador interpreta el esquema `javascript:` al principio del string y ejecuta el código `print()//http:` como JavaScript.
4. El `//` convierte el resto (`http:`) en un comentario de JS, así que no interfiere ni da error de sintaxis.

**En resumen:**

- La coma y el asterisco funcionan igual que antes (mensaje + `targetOrigin` abierto a cualquiera).
- El asterisco `*` sigue siendo el problema de origen "ancho".
- Pero aquí la vulnerabilidad real está en el **filtro del lado receptor**: comprobar `indexOf('http:')` en vez de validar correctamente que la URL comience con un esquema seguro (por ejemplo con `url.startsWith('https://')` y además comprobando `e.origin`).
