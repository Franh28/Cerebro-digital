
**El contexto: ¿qué hace vulnerable a la página?**

La home page del sitio guarda en una cookie, `lastViewedProduct`, la URL del último producto que visitaste. Esto lo hace del lado del cliente (JavaScript), probablemente algo como:

js

```js
document.cookie = "lastViewedProduct=" + location.href;
```

Y en algún momento, la home page **lee esa cookie y la inyecta en el HTML sin sanitizar** (por ejemplo, para mostrar un enlace "Volver a tu último producto visto"). Como no se sanitiza, si consigues que el valor de la cookie contenga HTML/JS, se ejecutará cuando la home page lo renderice. Eso es el **DOM XSS vía cookie manipulada**.

**El payload:**

html

```html
<iframe src="https://TU-LAB-ID.web-security-academy.net/product?productId=1&'><script>print()</script>" onload="if(!window.x)this.src='https://TU-LAB-ID.web-security-academy.net';window.x=1;">
```

Vamos por partes:

**1. El `src` inicial del iframe:**

```
/product?productId=1&'><script>print()</script>
```

Es una URL de producto normal, pero con basura añadida al final: `'><script>print()</script>`. Esto es el **payload XSS** que quieres que acabe guardado en la cookie `lastViewedProduct`. Cuando el iframe carga esta URL por primera vez, el script de la página de producto coge `location.href` (que incluye toda esta cadena, payload incluido) y la guarda tal cual en la cookie.

**2. El `onload`:**

js

```js
if (!window.x) this.src = 'https://TU-LAB-ID.web-security-academy.net'; window.x = 1;
```

Esto es la parte que generaba tu confusión ("lo del window"). Es un pequeño truco para controlar qué pasa **cada vez que el iframe termina de cargar** (el evento `onload` se dispara más de una vez: una vez para la carga inicial, y otra vez para la segunda carga que tú mismo provocas).

- `window.x` es una variable global que usas como "bandera"/flag, inicialmente `undefined` (es decir, "falsy").
- **Primera vez que carga el iframe** (con la URL del producto + payload): `window.x` todavía no existe → `!window.x` es `true` → se ejecuta `this.src = 'https://TU-LAB-ID.web-security-academy.net'`, es decir, **rediriges el propio iframe a la home page**. Justo después, `window.x = 1`, así que la bandera queda marcada como "ya hecho".
- Ese cambio de `src` hace que el iframe **vuelva a cargar**, esta vez apuntando a la home page → esto dispara el evento `onload` **por segunda vez**.
- **Segunda vez que carga el iframe** (ahora con la home page): `window.x` ya vale `1` → `!window.x` es `false` → el `if` no se ejecuta, así que el iframe se queda tranquilamente mostrando la home page, sin bucles infinitos.

**¿Por qué todo este rodeo?**

El objetivo es que la víctima:

1. Cargue brevemente, sin darse cuenta (dentro del iframe, de forma invisible/rápida), la URL maliciosa del producto → esto hace que su navegador guarde el payload en la cookie `lastViewedProduct`.
2. Inmediatamente después sea redirigida a la home page real → donde esa cookie envenenada se lee y se inyecta en el DOM sin sanitizar → se ejecuta `print()`.
