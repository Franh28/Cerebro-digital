La cabecera `X-Forwarded-Host` es una cabecera HTTP **no estándar pero muy común** que se usa en arquitecturas donde hay un proxy, balanceador de carga o CDN delante del servidor de aplicación real.

### Para qué sirve legítimamente

Cuando un cliente hace una petición, normalmente pasa por algo así:

```
Cliente → Proxy/Load Balancer → Servidor de aplicación
```

El problema es que, desde el punto de vista del **servidor de aplicación**, la petición parece venir del proxy, no del cliente original. Así que el servidor pierde información como:

- ¿Qué host/dominio pidió realmente el cliente? (`Host` header original)
- ¿Qué IP tiene el cliente real?
- ¿Usó HTTP o HTTPS?

Para solucionar esto, el proxy añade cabeceras adicionales antes de reenviar la petición al backend:

|Cabecera|Para qué sirve|
|---|---|
|`X-Forwarded-For`|IP real del cliente|
|`X-Forwarded-Proto`|Protocolo original (http/https)|
|`X-Forwarded-Host`|El **Host** que el cliente pidió originalmente|

**Ejemplo típico:** una app está detrás de Cloudflare o un load balancer de AWS. El backend recibe las peticiones con `Host: internal-server-01`, pero necesita saber que el usuario en realidad visitó `miapp.com` para poder generar links absolutos correctos (como los de "reset de contraseña", redirects, etc.). Ahí es donde el proxy le dice al backend, vía `X-Forwarded-Host: miapp.com`, cuál era el dominio real.

### Por qué es peligrosa si se confía ciegamente en ella

El problema de seguridad aparece cuando la aplicación **confía en el valor de esta cabecera sin validarlo**, asumiendo que solo el proxy legítimo puede ponerla. Pero en realidad, **cualquier cliente puede enviar esa cabecera directamente**, saltándose al proxy o incluso sin que exista proxy alguno.

En el lab que estás resolviendo:

1. La aplicación usa `X-Forwarded-Host` (pensando que refleja el dominio "real" desde el que se accede) para **construir el link absoluto** que manda en el email de reset de contraseña.
2. Como no valida que ese valor sea realmente uno de sus dominios de confianza, tú puedes poner el dominio que quieras (tu exploit server).
3. Resultado: el link de reset de la víctima apunta a tu servidor, y cuando ella (o el "bot" que simula la víctima) hace clic, el token de reset viaja hasta tu access log.

Este patrón de vulnerabilidad se llama **Host Header Injection** (o en este caso específico, **password reset poisoning via X-Forwarded-Host**), y es una variante de las vulnerabilidades más generales de "Host header attacks" que PortSwigger tiene en su Web Security Academy.
