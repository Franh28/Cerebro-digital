### ¿Qué ataque es este?

Se llama **"JWT authentication bypass via jku header injection"**. Es parecido al anterior (confías la clave pública al propio token), pero en vez de meter la clave pública directamente dentro del JWT (`jwk`), le dices al servidor **dónde ir a buscarla** mediante una URL (`jku` = "JWK Set URL").

#### Concepto: el parámetro `jku`

Algunos servidores, en vez de tener su clave pública fija y conocida de antemano, permiten que el propio JWT les diga: "oye, para verificar mi firma, ve a buscar la clave pública en esta URL". Esa URL apunta a un documento JSON llamado **JWK Set** (un conjunto de claves públicas en formato estándar).

**El fallo de seguridad**: si el servidor confía en **cualquier URL** que le pongas en el campo `jku` del header (sin comprobar que sea un dominio de confianza), tú puedes:

1. Generar tu propio par de claves (pública + privada)
2. Subir tu clave pública a un servidor que tú controlas (en este caso, el "exploit server" que da el lab de PortSwigger)
3. Poner en el token la URL de tu servidor en el campo `jku`
4. Firmar el token con tu clave privada
5. El servidor de la víctima va a tu URL, descarga tu clave pública, y la usa para verificar la firma
6. Como tú firmaste con tu clave privada correspondiente, todo "cuadra" y el servidor te cree

Es como si el portero, en vez de confiar en la clave pública que tú traes pegada en el DNI (ataque anterior), llamara por teléfono a un número que **tú mismo le proporcionas** para "verificar" tu identidad — obviamente tú contestas el teléfono y confirmas que todo está en orden.

### Preparación

Asumo que ya tienes la extensión JWT Editor instalada (si no: Extensions → BApp Store → "JWT Editor" → Install).

---

### Paso 1: Confirmar que /admin está bloqueado

1. Inicia sesión en el lab con tu cuenta normal
2. Ve a **Proxy** → **HTTP history**
3. Busca `GET /my-account` (justo después del login)
4. Click derecho → **Send to Repeater**
5. En Repeater, cambia la ruta a `/admin`
6. Click **Send**
7. Confirma que te deniega el acceso

---

### Paso 2: Generar tu propio par de claves RSA

1. Ve a la pestaña **JWT Editor Keys**
2. Click en **New RSA Key**
3. En el diálogo, click en **Generate** (crea el par de claves automáticamente)
4. Click **OK** para guardarla

Esta clave se queda guardada en Burp con un identificador (`kid`) único — lo necesitarás más adelante.

---

### Paso 3: Preparar tu "almacén" de claves públicas en el exploit server

El **exploit server** es un servidor controlado por ti que da el lab de PortSwigger (tiene su propia URL, distinta a la del lab). Lo vas a usar para alojar tu clave pública, simulando ser una fuente "externa" de confianza.

1. En el navegador, ve a la URL del **exploit server** (hay un botón "Go to exploit server" en la parte superior del lab)
2. Verás un formulario con una sección **Body** (el contenido que se servirá cuando alguien visite esa URL)
3. Borra lo que haya y pon un JWK Set vacío:

json

```json
{
    "keys": [

    ]
}
```

Esto define la estructura: un objeto con un array `keys` donde meterás tu clave pública.

---

### Paso 4: Copiar tu clave pública y pegarla en el exploit server

1. Vuelve a la pestaña **JWT Editor Keys** en Burp
2. Click derecho sobre la clave RSA que generaste en el Paso 2
3. Selecciona **Copy Public Key as JWK** (esto copia solo la parte pública de tu clave, en formato JSON, al portapapeles — NUNCA la privada, esa se queda solo en Burp)
4. Vuelve al navegador, al exploit server
5. Pega esa clave dentro del array `keys`, quedando algo así:

json

```json
{
    "keys": [
        {
            "kty": "RSA",
            "e": "AQAB",
            "kid": "893d8f0b-061f-42c2-a4aa-5056e12b8ae7",
            "n": "yy1wpYmffgXBxhAUJzHHocCuJolwDqql75ZWuCQ_cb33K2vh9mk6GPM9gNN4Y_qTVX67WhsN3JvaFYw..."
        }
    ]
}
```

6. Click en **Store** (guarda el contenido en tu exploit server, en una URL fija tipo `https://exploit-xxxxx.web-security-academy.net/`)

Ahora, si cualquiera visita esa URL, verá tu clave pública en formato JWK Set — exactamente lo que un servidor esperaría encontrar al consultar un `jku`.

---

### Part 2 — Modificar y firmar el JWT

#### Paso 5: Volver a la petición en Repeater

1. Ve a la petición `GET /admin` en Repeater
2. Abre la pestaña **JSON Web Token**

#### Paso 6: Igualar el `kid` del token con el de tu clave

1. En el **header** del JWT, busca el campo `kid`
2. Reemplázalo por el mismo `kid` que tiene tu clave en el exploit server (el que copiaste en el Paso 4 — debería ser el mismo que genera Burp automáticamente, cópialo tal cual de ahí)

Esto es importante porque cuando el servidor vaya a tu JWK Set, puede haber varias claves ahí dentro; usa el `kid` para saber cuál de ellas corresponde a este token.

#### Paso 7: Añadir el parámetro `jku`

1. En el mismo header, añade un nuevo campo:

json

```json
"jku": "https://TU-URL-DEL-EXPLOIT-SERVER/"
```

2. Pon ahí la URL exacta donde guardaste tu JWK Set en el Paso 4 (la del exploit server)

Con esto le estás diciendo al servidor del lab: "para verificar mi firma, ve a buscar las claves públicas en esta dirección".

#### Paso 8: Cambiar el payload

1. Busca en el payload:

json

```json
"sub": "wiener"
```

2. Cámbialo a:

json

```json
"sub": "administrator"
```

#### Paso 9: Firmar el token

1. Al final de la pestaña, click en **Sign**
2. Selecciona la clave RSA que generaste (la misma de antes)
3. Asegúrate de que esté marcada **"Don't modify header"** (para no perder los cambios que hiciste en `kid` y `jku`)
4. Click **OK**

Burp firma el token usando tu clave privada. La firma resultante solo se puede verificar correctamente con tu clave pública — la misma que subiste al exploit server.

---

### Paso 10: Enviar la petición

1. Asegúrate de que la ruta sigue siendo `/admin`
2. Click **Send**
3. El servidor del lab:
    - Lee el header, ve el `jku` apuntando a tu exploit server
    - Va a esa URL, descarga tu JWK Set
    - Busca dentro la clave con el `kid` que indicaste
    - Usa esa clave pública para verificar la firma del token
    - Como tú firmaste con la clave privada correspondiente, la verificación es válida
4. Deberías ver el panel de administración en la respuesta (200 OK)
