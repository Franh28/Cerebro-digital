### ¿Qué es un JWT y por qué importa?

Cuando inicias sesión en una web, el servidor necesita "recordar" quién eres en cada petición siguiente. Una forma de hacer esto es con un **JWT (JSON Web Token)**, que es como una tarjeta de identificación digital que tu navegador guarda (normalmente en una cookie) y envía en cada petición.

Un JWT tiene 3 partes separadas por puntos:

```
eyJhbGciOiJIUzI1NiJ9 . eyJzdWIiOiJ3aWVuZXIifQ . 8MysukrnDWhnp3cJ...
      HEADER                  PAYLOAD                SIGNATURE
```

- **Header**: dice qué algoritmo se usó para firmar (ej. `HS256`)
- **Payload**: contiene los datos, por ejemplo `{"sub":"wiener"}` — esto significa "este token pertenece al usuario wiener"
- **Signature (firma)**: es un sello criptográfico que demuestra que el servidor generó este token y que nadie lo ha modificado

El header y el payload están solo en **Base64** (no cifrados), así que cualquiera puede leerlos e incluso modificarlos fácilmente. Lo que impide que alguien se haga pasar por otro usuario es la **firma**. El servidor, al recibir el token, recalcula la firma usando su clave secreta y la compara con la que viene en el token. Si no coincide, lo rechaza.

**El objetivo del ataque**: si logramos saber cuál es esa clave secreta, podemos nosotros mismos crear un token falso diciendo "soy el administrator" y firmarlo correctamente, de modo que el servidor lo acepte como válido.

### Preparación: Instalar la extensión JWT Editor

Burp Suite no trae de serie herramientas para editar JWTs fácilmente, así que instalamos una extensión.

1. Abre **Burp Suite**
2. Ve a la pestaña **Extensions** (arriba)
3. Click en **BApp Store** (dentro de Extensions)
4. En el buscador, escribe **JWT Editor**
5. Selecciónalo y click en **Install**

Esto añade dos cosas nuevas a Burp:

- Una pestaña nueva llamada **JWT Editor Keys** (arriba del todo, junto a Proxy, Repeater, etc.)
- Un sub-panel llamado **"JSON Web Token"** que aparecerá automáticamente dentro de Repeater cada vez que una petición contenga un JWT

### Part 1 — Averiguar la clave secreta del servidor (Brute-force)

#### Paso 1: Inicia sesión en el laboratorio

- Entra a la web del lab de PortSwigger con tu usuario de prueba (normalmente `wiener` / `peter`)
- Asegúrate de que **Burp Proxy** está interceptando o al menos registrando el tráfico (el navegador debe estar configurado para pasar por Burp, normalmente usando el navegador integrado de Burp)

#### Paso 2: Captura la petición a /my-account

- Justo después de iniciar sesión, la web hace una petición `GET /my-account`
- Ve a la pestaña **Proxy** → **HTTP history** en Burp
- Busca esa petición en la lista
- Click derecho sobre ella → **Send to Repeater**

#### Paso 3: Intenta acceder a /admin

- Ve a la pestaña **Repeater** (ahí debería estar la petición que acabas de enviar)
- En la parte donde dice la ruta (ej. `GET /my-account HTTP/2`), cámbiala a:

```
  GET /admin HTTP/2
```

- Click en **Send**
- Observa la respuesta: debería darte un error (403 Forbidden o similar), porque tu usuario normal no tiene permisos de admin

Esto confirma que hay una zona protegida (`/admin`) a la que solo debería entrar el usuario `administrator`.

#### Paso 4: Copia el JWT completo

- En la petición (panel izquierdo de Repeater), busca la cabecera:

```
  Cookie: session=eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJ3aWVuZXIifQ.8MysukrnDW...
```

- Selecciona y copia **todo el valor** después de `session=` (las tres partes con los dos puntos)

#### Paso 5: Crackear la clave con Hashcat (fuera de Burp)

Aquí sales de Burp y usas un programa externo llamado **hashcat**, que sirve para "adivinar" contraseñas/claves probando muchísimas combinaciones de un diccionario.

**¿Por qué funciona esto?** Porque muchos desarrolladores, por error o pereza, usan palabras simples y predecibles como clave secreta (`secret1`, `password`, etc.) en vez de una clave aleatoria larga. Hashcat prueba miles de palabras candidatas de una lista y comprueba, para cada una, si al firmar el JWT con esa palabra se obtiene la misma firma que tiene tu token real.

1. Abre una terminal (CMD/PowerShell en Windows)
2. Necesitas tener descargado el archivo `jwt.secrets.list` (una lista de palabras candidatas; viene en los materiales del lab de PortSwigger)
3. Ejecuta:

```
hashcat -a 0 -m 16500 <TU-JWT-COMPLETO> C:\ruta\a\jwt.secrets.list
```

- `-a 0` → modo "ataque de diccionario" (prueba palabra por palabra de la lista)
- `-m 16500` → le dice a hashcat "esto es un JWT, trátalo con ese algoritmo específico"

Si tiene éxito, verás una línea como:

```
eyJhbGci...8MysukrnDW...:secret1
```

Todo lo que va **después de los dos puntos finales** es la clave secreta descubierta: en este caso, `secret1`.

(Si vuelves a ejecutar el comando más tarde, hashcat ya lo tiene guardado y no lo vuelve a mostrar solo; tienes que añadir `--show` al final para volver a verlo.)

### Part 2 — Crear una clave falsificada dentro de Burp

Ahora que sabemos cuál es el secreto, tenemos que "enseñarle" a Burp esa clave para que pueda firmar tokens igual que lo haría el servidor real.

#### Paso 1: Convertir el secreto a Base64

Los JWT internamente trabajan con las claves en formato Base64, así que primero hay que convertir `secret1` a ese formato.

1. En Burp, ve a la pestaña **Decoder**
2. En el cuadro de texto, escribe o pega: `secret1`
3. A la derecha verás opciones; busca el desplegable **Encode as...**
4. Selecciona **Base64**
5. Esto te genera algo como: `c2VjcmV0MQ==`
6. Copia ese resultado codificado

#### Paso 2: Crear una clave simétrica en JWT Editor

1. Ve a la pestaña **JWT Editor Keys** (añadida por la extensión)
2. Click en **New Symmetric Key**
3. Se abre un diálogo con campos como `kty`, `kid`, `k` ya rellenados con valores de ejemplo aleatorios generados automáticamente
4. Click en **Generate** si no se generó nada aún (esto solo crea un ejemplo base, lo vamos a sobrescribir)

#### Paso 3: Insertar tu clave real

1. Busca dentro de ese JSON el campo que dice `"k": "..."`
2. Borra el valor que hay ahí
3. Pega el Base64 que generaste en el paso anterior (`c2VjcmV0MQ==`)
4. Deja los demás campos (`kty`, `kid`, etc.) como están

#### Paso 4: Guardar

- Click en **OK**
- Ahora Burp tiene guardada una clave que es idéntica a la que usa el servidor para firmar. La verás listada en la pestaña JWT Editor Keys.

### Part 3 — Falsificar el token y colarte como admin

#### Paso 1: Vuelve a la petición en Repeater

- Ve otra vez a la petición `GET /admin` que tienes en Repeater (la misma de antes)

#### Paso 2: Abre la pestaña del token

- Dentro de Repeater, junto a "Pretty", "Raw", "Hex", ahora debería aparecer una pestaña nueva: **JSON Web Token**
- Click ahí — verás el header y el payload del JWT ya separados y legibles, en formato editable

#### Paso 3: Cambia quién eres

- Busca en el payload la línea:

json

```json
  "sub": "wiener"
```

- Cámbiala a:

json

```json
  "sub": "administrator"
```

Esto le está diciendo al token "represento al usuario administrator" — pero todavía la firma no coincide con este cambio, así que si lo envías ahora, fallará.

#### Paso 4: Firma el token con tu clave falsa

- Abajo en ese mismo panel hay un botón **Sign**
- Click ahí
- Te preguntará qué clave usar para firmar → selecciona la clave que creaste en Part 2 (la que contiene `secret1` en Base64)
- Asegúrate de que la casilla **"Don't modify header"** esté marcada (para no tocar el algoritmo ni otros metadatos)
- Click **OK**

Lo que ocurre aquí: Burp toma tu nuevo payload (`administrator`), lo firma usando la misma clave secreta que usa el servidor (`secret1`), y genera una firma nueva **matemáticamente correcta**. El servidor no tiene forma de saber que no fue él quien creó este token, porque la firma es válida.
