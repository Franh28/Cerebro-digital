### ¿Qué ataque es este?

Se llama **"JWT authentication bypass via kid header path traversal"**. Explota cómo algunos servidores usan el campo `kid` del header.

#### Concepto: ¿para qué sirve normalmente el `kid`?

El campo `kid` (Key ID) sirve para que el servidor sepa **qué clave usar** para verificar la firma, cuando tiene varias claves disponibles. Normalmente el servidor tiene algo así internamente:

```
claves = {
  "clave-001": "s3cr3t-aleatorio-1",
  "clave-002": "otro-secreto-2"
}
```

Y cuando recibe un JWT, mira el `kid` y busca esa clave en su almacén.

#### El fallo de este servidor en concreto

Este servidor, en lugar de buscar el `kid` en una lista fija de claves de confianza, usa el valor del `kid` directamente como **ruta a un archivo en el sistema operativo**, y lee el contenido de ese archivo para usarlo como clave secreta de verificación.

Es decir, hace algo parecido (conceptualmente) a:

```
contenido_clave = leer_archivo("/ruta/base/" + kid)
```

**El problema**: si tú controlas el valor de `kid`, puedes usar una técnica llamada **path traversal** (`../../../`) para escapar de la carpeta esperada y apuntar a **cualquier archivo del sistema**. Y aquí está el truco genial: apuntas a `/dev/null`.

#### ¿Qué es `/dev/null`?

En sistemas Linux, `/dev/null` es un archivo especial que **siempre existe** y **siempre está vacío** (0 bytes). No importa qué sistema sea, casi con total seguridad existe y no tiene contenido.

Entonces, si logras que el servidor lea `/dev/null` como si fuera la clave secreta, está usando efectivamente una **clave vacía** (string vacío, o en términos técnicos, un conjunto de "cero bytes") para firmar/verificar.

Como tú también sabes que la clave va a ser "vacía", puedes firmar tu propio token usando una clave vacía — ¡y coincidirá perfectamente con lo que el servidor calculará!

---

### Paso 1: Confirmar que /admin está bloqueado

1. Inicia sesión en el lab con tu cuenta normal
2. Ve a **Proxy** → **HTTP history**, busca `GET /my-account` (justo tras el login)
3. Click derecho → **Send to Repeater**
4. En Repeater, cambia la ruta a `/admin`
5. Click **Send**
6. Confirma que te deniega el acceso

---

### Paso 2: Crear una clave simétrica VACÍA

Aquí, en vez de generar un secreto real o crackear uno, vas a crear una clave cuyo valor está **deliberadamente vacío**, para que coincida con lo que el servidor "encontrará" en `/dev/null`.

1. Ve a la pestaña **JWT Editor Keys**
2. Click en **New Symmetric Key**
3. En el diálogo, click en **Generate** (esto rellena los campos con valores de ejemplo, incluido el campo `k`)
4. Busca el campo `k` dentro del JSON generado
5. Borra su contenido y déjalo como **cadena vacía**: `""`
6. Click **OK** para guardar

Ahora tienes una clave en Burp cuyo valor es literalmente "nada" — igual que el contenido de `/dev/null`.

---

### Paso 3: Modificar el header — ataque de path traversal en `kid`

1. Vuelve a la petición `GET /admin` en Repeater
2. Abre la pestaña **JSON Web Token**
3. En el **header**, busca el campo `kid`
4. Reemplaza su valor actual por esta secuencia de path traversal:

```
../../../../../../../dev/null
```

Esto le dice al servidor (si es vulnerable): "la clave que debes usar se llama `../../../../../../../dev/null`" — y como el servidor construye la ruta del archivo concatenando esto a su carpeta base de claves, las secuencias `../` lo hacen "subir" de carpeta en carpeta hasta salir de donde debería estar, llegando finalmente a la raíz del sistema de archivos (`/`) y entrando en `/dev/null`.

(El número de `../` suele ser más de los necesarios a propósito, para asegurar que llegas a la raíz sin importar cuán profunda esté la carpeta original — de más no hace daño, el sistema simplemente no puede subir más allá de la raíz.)

---

### Paso 4: Modificar el payload

1. En el **payload**, busca:

json

```json
"sub": "wiener"
```

2. Cámbialo a:

json

```json
"sub": "administrator"
```

---

### Paso 5: Firmar con la clave vacía

1. Al final de la pestaña, click en **Sign**
2. Selecciona la clave simétrica que creaste en el Paso 2 (la del valor `k` vacío)
3. Asegúrate de que **"Don't modify header"** esté marcada (crucial — si no, Burp podría sobrescribir tu `kid` manipulado)
4. Click **OK**

Burp firma el token usando "nada" como clave (HMAC con clave vacía). Si el servidor, al verificar, también termina usando "nada" (porque leyó `/dev/null`, que está vacío), las firmas coincidirán.

---

### Paso 6: Enviar la petición

1. Asegúrate de que la ruta sigue siendo `/admin`
2. Click **Send**
3. Si el servidor es vulnerable (como en este lab):
    - Lee el `kid`, lo usa para construir una ruta de archivo
    - El path traversal lo lleva a `/dev/null`
    - Lee ese archivo (vacío) y lo usa como clave secreta
    - Verifica tu firma con esa clave vacía → coincide, porque tú también firmaste con clave vacía
4. Deberías ver el panel de administración en la respuesta (200 OK)
