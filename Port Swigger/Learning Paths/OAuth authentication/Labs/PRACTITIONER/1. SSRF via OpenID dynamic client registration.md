### El concepto central

Este lab combina dos cosas:

1. **Registro dinámico de clientes OpenID**: muchos servidores OAuth permiten que cualquier aplicación se registre a sí misma como "cliente" sin autenticación previa, enviando un POST a un endpoint tipo `/reg`. Esto es parte del estándar (OpenID Dynamic Client Registration).
2. **SSRF (Server-Side Request Forgery)**: cuando registras un cliente, puedes indicar propiedades como `logo_uri` (la URL del logo de tu app). El servidor OAuth, en algún momento, va a **buscar esa imagen desde su propio backend** para mostrarla en la pantalla de autorización. Si no valida esa URL, puedes hacer que el servidor haga peticiones a donde tú quieras — incluyendo servicios internos.

El objetivo final es explotar esto para llegar a `169.254.169.254`, que es la **dirección de metadatos de instancia en AWS** (un endpoint interno accesible solo desde dentro de la máquina/VPC). Ahí se guardan credenciales temporales de IAM — si el servidor hace la petición por ti, te las puede filtrar.

### Desglose del flujo de ataque

**1. Descubrir el endpoint de registro**  
Visitas `/.well-known/openid-configuration`, que es un archivo estándar que describe toda la configuración del servidor OAuth (endpoints de autorización, token, userinfo, y en este caso, `registration_endpoint` → `/reg`).

**2. Registrar un cliente falso**  
Haces un `POST /reg` con un JSON mínimo (`redirect_uris`). Como es registro dinámico sin autenticación, el servidor te acepta y te da un `client_id` nuevo, sin preguntas.

**3. Encontrar dónde se usa el `logo_uri`**  
Al revisar el flujo de autorización (la pantalla donde el usuario da consentimiento), ves que carga el logo desde `/client/CLIENT-ID/logo`. Esto te dice que el servidor **va a buscar esa imagen por su cuenta** — ahí está tu vector de SSRF.

**4. Confirmar el SSRF con Burp Collaborator**  
Registras otro cliente, esta vez con `logo_uri` apuntando a un dominio de Burp Collaborator (un servicio que te da un dominio único y te avisa si alguien le hace una petición). Si al pedir `/client/CLIENT-ID/logo` ves una interacción en Collaborator, confirmas que el servidor efectivamente hizo la petición saliente — SSRF confirmado.

**5. Apuntar al endpoint de metadatos interno**  
Ahora que sabes que funciona, repites el registro pero con:

```
"logo_uri": "http://169.254.169.254/latest/meta-data/iam/security-credentials/admin/"
```

Esta URL interna devuelve credenciales temporales de IAM para el rol "admin" de la instancia EC2.

**6. Robar las credenciales**  
Cuando pides `/client/CLIENT-ID/logo` con el nuevo `client_id`, el servidor OAuth hace la petición a ese endpoint interno _en tu nombre_ y te devuelve el contenido como si fuera el logo — pero en realidad es el JSON con la `AccessKeyId`, `SecretAccessKey` y `Token`.

### Por qué funciona

El fallo de raíz es que el servidor **confía ciegamente en una URL proporcionada por el cliente** y la usa para hacer una petición server-side, sin:

- Validar que sea una URL "razonable" para un logo (imagen, dominio público, etc.)
- Bloquear rangos de IP internos/reservados (como 169.254.0.0/16, 127.0.0.1, 10.0.0.0/8, etc.)

Esto es un caso clásico de SSRF, pero con un giro: el vector no es un campo obvio como "URL de callback de pago", sino una característica secundaria del estándar OpenID (metadata de registro de cliente) que nadie pensó en tratar como entrada no confiable.
