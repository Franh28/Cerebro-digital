1. Try to load `/admin` and observe that you get blocked. Notice that the response is very plain, suggesting it may originate from a front-end system.
2. Send the request to Burp Repeater. Change the URL in the request line to `/` and add the HTTP header `X-Original-URL: /invalid`. Observe that the application returns a "not found" response. This indicates that the back-end system is processing the URL from the `X-Original-URL` header.
3. Change the value of the `X-Original-URL` header to `/admin`. Observe that you can now access the admin page.
4. To delete `carlos`, add `?username=carlos` to the real query string, and change the `X-Original-URL` path to `/admin/delete`.


Para ver si el framework soporta X-Original-URL, puedes hacer lo del paso 2, o esto:

### 1. Prueba Activa con `cURL` o Postman (Recomendado)

La forma más rápida es enviar peticiones HTTP manipuladas y observar la respuesta del servidor. Necesitas un endpoint que sepas que existe (ej. `/login` o `/` que devuelva 200 OK) y uno que no exista (que devuelva 404 Not Found).

**Prueba A: Sobrescribir una ruta válida a una inválida** Envía una petición a una ruta válida, pero añade la cabecera apuntando a una ruta que no existe:

Bash

```
curl -i -s -k -X GET -H "X-Original-URL: /ruta-que-no-existe" https://tu-sitio.com/
```

- **Si el framework la soporta:** El servidor te devolverá un error **404 Not Found** (está leyendo la cabecera en lugar de la URL real `/`).
    
- **Si no la soporta:** Devolverá **200 OK** (ignoró la cabecera).
    

**Prueba B: Sobrescribir una ruta inválida a una válida** Envía una petición a una ruta que no existe, pero usa la cabecera apuntando a una ruta válida:

Bash

```
curl -i -s -k -X GET -H "X-Original-URL: /" https://tu-sitio.com/ruta-que-no-existe
```

- **Si el framework la soporta:** Devolverá **200 OK** (cargó la página principal `/`).
    

### 2. Revisión de la Documentación y Código Fuente

Busca en la documentación oficial del framework apartados sobre "URL Rewriting", "Reverse Proxy Configuration" o "Trusted Proxies".

A nivel de código, si tienes acceso, busca en el middleware de enrutamiento (Routing) o en el objeto que maneja la Request HTTP. Históricamente, algunos frameworks conocidos han tenido este comportamiento por defecto:

- **Symfony (PHP):** Antiguamente confiaba en `X-Original-URL` y `X-Rewrite-URL` (solucionado en CVE-2018-14773, ahora requiere configuración estricta de _trusted proxies_).
    
- **Zend Framework / Laminas (PHP):** Suele tener soporte para estas cabeceras en sus clases de Request.
    
- **ASP.NET / IIS:** Es muy común que se utilicen módulos de reescritura de URL que interactúan con estas cabeceras.
    

### 3. Herramientas de Seguridad Automáticas

Si estás auditando la seguridad de la aplicación, herramientas como **Burp Suite** (con la extensión _Param Miner_) o **Nuclei** tienen _templates_ específicos para detectar si una aplicación es vulnerable a "Routing Bypass" mediante `X-Original-URL`.

> **⚠️ Advertencia de Seguridad:** Si tu framework confía en esta cabecera y no estás validando correctamente quién te la envía (es decir, no estás descartando las cabeceras inyectadas por el usuario final antes de que lleguen al proxy/WAF), tu aplicación podría ser vulnerable a **Bypass de Autenticación o Bypass de WAF**. Un atacante podría saltarse restricciones accediendo a `/admin` mediante una petición engañosa.

¿Cómo mitigar y protegerme contra ataques de bypass de rutas usando X-Original-URL?

Para proteger tu aplicación contra ataques de bypass de rutas mediante cabeceras como `X-Original-URL` o `X-Rewrite-URL`, el objetivo principal es **romper la confianza ciega** entre el cliente, el proxy (front-end) y la aplicación (back-end).

La vulnerabilidad existe porque el back-end confía en una cabecera que puede ser manipulada por el usuario, mientras que el front-end solo inspecciona la línea principal de la petición.

Aquí tienes las estrategias clave para mitigar y erradicar este riesgo, ordenadas por efectividad:

### 1. Eliminación de Cabeceras en el Proxy (Header Stripping)

La defensa más robusta es configurar tu proxy inverso, balanceador de carga o WAF (Web Application Firewall) para que **elimine estas cabeceras si provienen del cliente**, antes de que la petición llegue al back-end. De esta forma, el atacante nunca podrá inyectarlas.

**En Nginx:** Puedes vaciar el valor de la cabecera al pasar la petición al back-end:

Nginx

```
location / {
    proxy_set_header X-Original-URL "";
    proxy_set_header X-Rewrite-URL "";
    proxy_pass http://backend;
}
```

**En Apache:** Usa el módulo `mod_headers` para destruir la cabecera maliciosa:

Apache

```
<IfModule mod_headers.c>
    RequestHeader unset X-Original-URL
    RequestHeader unset X-Rewrite-URL
</IfModule>
```

### 2. Desactivar el soporte en el Framework (Back-end)

Si tu aplicación no necesita utilizar estas cabeceras para reescritura de URLs legítima, lo mejor es instruir al framework para que las ignore por completo.

- **Configuración de Proxies Confiables (Trusted Proxies):** Frameworks modernos como Symfony, Laravel (PHP) o Spring (Java) procesan ciertas cabeceras (como `X-Forwarded-*` o `X-Original-URL`) **solo** si provienen de una dirección IP definida explícitamente como "Proxy de confianza". Asegúrate de tener esta lista estrictamente configurada.
    
- **Actualización del Framework:** Muchas de estas vulnerabilidades (como CVE-2018-14773 en Symfony) fueron parcheadas hace años. Mantener las dependencias actualizadas asegura que el framework adopte comportamientos seguros por defecto.
    

### 3. Defensa en Profundidad: Controles de Acceso Estrictos

El error de diseño fundamental en los bypass de rutas es delegar toda la seguridad de acceso al proxy o WAF basándose únicamente en la URL.

- **Validación en el Controlador:** No confíes solo en que el WAF bloqueará las peticiones a `/admin`. El código que se ejecuta al cargar el panel de administración debe verificar activamente si el usuario actual tiene una sesión válida y el rol de administrador asignado.
    
- **Principio de Mínimo Privilegio:** Si un atacante logra evadir la regla de enrutamiento y llega a la función de "eliminar usuario", la aplicación debería rechazar la acción porque detectará que la petición se está haciendo sin las cookies o tokens de autorización de un administrador.
    

### 4. Normalización de URLs

Asegúrate de que tanto el front-end como el back-end procesen y normalicen las URLs de la misma manera. Las discrepancias en cómo los servidores interpretan rutas (por ejemplo, el uso de barras finales `/admin` vs `/admin/`, o caracteres codificados `%2e%2e/`) son la base de la mayoría de ataques de desincronización y bypass.
